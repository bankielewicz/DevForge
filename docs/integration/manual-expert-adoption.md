# Manual Codex expert adoption

This implements the F06 adoption prerequisite for `devforge-project-expert-creator` and `devforge-evaluate-expert`. The trusted installer requires current evidence before its operational writes. It does not intercept authoring phase order, arbitrary shell/editor writes, user invocation, or native execution. The user initiates skills, transfers their real artifacts, and initiates commands. Automated orchestration remains deferred; managed v1 workflow IDs and funded-launch refusals are unchanged.

## Scope and commands

The integration owner refreshes only the promoted Codex packages:

```text
python3 scripts/install_framework.py --framework FRAMEWORK --project PROJECT --provider codex --manual-experts-only --manual-evidence ADOPTION_RECORD
```

The same manual-only path exists as compiled Rust in the DevForge CLI, which owns the evidence validation, acceptance predicates and installation writes without consulting Python:

```text
devforge install manual-experts --project PROJECT --framework FRAMEWORK --evidence ADOPTION_RECORD --authority AUTHORITY_RECORD
```

A check-only companion reads the same evidence through the same Rust functions and reports whether it is mechanically consumable, without installing anything (see [Local evidence preflight](#local-evidence-preflight)):

```text
devforge install check-local-evidence --project PROJECT --framework FRAMEWORK --packet PREFLIGHT_PACKET --authority AUTHORITY_RECORD
```

`devforge install manual-experts` implements only this mode: the recognized Codex packages present in the framework, `.agents/skills` destinations, authoring-only retirement, local-edit/collision refusal, the record shapes and refusal reasons below, and the `.devforge-install.json` inventory (`files`, `managed_hooks`, `runtime_evidence` and other existing fields are preserved; `manual_expert_adoption` is updated exactly as the legacy installer records it). Whole-framework installation (Claude, Codex or both, `--include-experts`, delivery runtime probes and hook merging) is `devforge install framework`, and plugin export is `devforge install export-plugin` (see [framework installation](framework-installation.md)); `manual-experts` does not accept those options. The legacy script's `--manual-experts-only` refresh is the only installation mode still implemented in Python. Refusals print the JSON `BLOCKED` object with exit 2 before any installation write; success prints `INSTALLED` with `authority: "compiled Rust CLI; no Python consulted"`, `behavior: NOT_EVALUATED` and the verified `protected_identity`.

The additional `--authority` record is the owner-controlled binding required by the [development language policy](../development-language-policy.md). It must be outside the project and the framework and has exactly:

```json
{
  "schema_version": "devforge.manual-install-authority/v1",
  "owner": "ACTUAL_INTEGRATION_OWNER",
  "executable": {"path": "/protected/devforge", "sha256": "ACTUAL_SHA256"},
  "source_sha256": "ACTUAL_SOURCE_IDENTITY"
}
```

`devforge install identity` prints the running executable's canonical path and SHA-256 together with `source_sha256`, the content identity of `Cargo.toml`, `Cargo.lock`, `build.rs`, `src/`, `runners/` and `runtime/delivery/` that `build.rs` embeds at compile time. Before any evidence is read, and again immediately before installation writes, the CLI refuses unless its own canonical path and digest equal the pinned executable and its embedded source identity equals `source_sha256`. A rebuilt binary, a copy at another path, or a build from a changed source tree cannot satisfy an unchanged authority record even when it reports the same version. This self-check is not tamper protection on its own: the owner must launch the pinned binary from a location the evaluated agent cannot write (for example under `devforge isolate`, where only the project is writable) and keep the authority record, framework and evidence records outside that boundary. The identity binds file content only; it does not cover the Rust toolchain or a Git revision.

The preflight also inspects destination aliases. Every existing destination inode is collected with the payload it would receive; an inode reachable through two destinations with differing payloads is refused (`destination alias would receive conflicting replacement payloads`), an inode that is the selected authority record or the running executable is refused whatever the payload, and an inode that is pinned evidence is refused unless the payload equals the pinned digest. After the evidence recheck, the authority record and executable are verified again and must match the values checked before evidence was read. A symlinked promoted skill source is refused (`missing or symlink source directory`), as the legacy installer refuses it, rather than being omitted from the selection. Timestamps keep the contract the legacy guard accepted through `datetime.fromisoformat`, including basic forms such as `20260908T120001+0000`, ISO week dates (week 53 only in a long ISO year, so `2021-W53-1` is refused as the legacy guard refused it), a fraction after the last time component, and offsets down to fractional seconds such as `+00:00:01.5`, which shift the compared instant. The offset uses the same `HH[[:]MM[[:]SS]][.frac]` grammar as the time (`+00:01.5` is 60.5 s, `+2359.5` is 23 h 59 min 0.5 s); minute or second fields above 59 are summed as the legacy parser summed them, and the total must stay under 24 hours. As in the legacy parser, an offset fraction counts only when the whole offset is non-zero: `+00:00:00.5` and `+00:00.5` are UTC, so a set frozen at `12:00:00.2+00:00:00.5` is still after a `12:00:00.1+00:00` start and is refused as not predefined. A missing offset remains `invalid timestamp`.

Rust acceptance tests in `tests/manual_install.rs` drive the compiled binary with synthetic Full, Routine and local-baseline fixtures equivalent to the legacy Python cases, identity refusals (changed executable digest, changed source identity, a copied executable at another path, an authority record inside the project or framework), and the alias, symlink and timestamp regressions above; two of those invoke the unchanged legacy installer only as a compatibility baseline. The unchanged Python suites still exercise the legacy Python installer and are not evidence for the Rust path. The Rust tests cannot inject the mid-run evidence drift that the Python mock-based cases simulate; the final rechecks exist but that race is not black-box tested.

Destination checks and writes are path based (check-then-use), in Rust as in the legacy installer. A process that can write to the project concurrently could replace a checked directory with a symlink between the preflight and a write, and nothing here defends against that. Operational precondition: run `install manual-experts` from the authority terminal only while the project is quiescent, meaning no evaluated agent, `devforge isolate` session or other writer holds write access to that project for the duration of the command. No existing DevForge mechanism establishes or verifies this: the gate lock in `<state>/.lock` covers gate runs, not installation, and `isolate` confines a client to the project rather than stopping it writing there. Until the owner meets that precondition procedurally or a separately assigned bounded Rust write-containment change (directory-descriptor-relative, no-follow opens) is delivered, treat concurrent project mutation during installation as an unresolved prerequisite, not a protected case.

`--manual-experts-only` selects recognized promoted packages present in the chosen framework and preserves other skills, agents, hook settings and runtime inventories. It cannot combine with `--include-experts` or a different provider. Without this flag, ordinary installation retains its existing provider/runtime checks and also requires adoption evidence when either promoted Codex identity is included. Recognized names cannot opt out by omitting a candidate-owned profile. Claude is unchanged.

The record must be selected by the actual integration owner. Its named producer strings and digests cannot authenticate people or prove model behavior. The independent reviewer and operator must examine actual retained outputs, source/history/output boundaries, native observations and real user-mediated transfer before selecting acceptance. A synthetic fixture, advisory reducer PASS, or the package author's report cannot provide that authority. Conditional installation authority already supplied by the user need not be requested again after its conditions pass.

For pre-adoption native resource testing, `devforge install export-plugin --framework FRAMEWORK --provider codex --output NEW/devforgeai` (or the unchanged legacy `--export-plugin NEW/devforgeai --provider codex`) remains available. It reports `adoption: NOT_ACCEPTED_STAGING` and omits source-only evals. It does not enable a package in this project's operational discovery directory. Treat manually loading an exported plugin as an allocated test action, not operational acceptance. No managed advance/resume/complete fallback is used.

All evidence refusals return the existing JSON `BLOCKED` with exit 2 before installation writes. Missing/extra files, unsupported or duplicate record data, stale pins, incomplete case/phase/task evidence, changed classifications, self-review, unsupported Routine eligibility and missing Full receiving references refuse. Existing local-edit/hook/runtime collision checks remain. The final preflight rechecks evidence and refuses writes that would invalidate its own selected evidence. Installed bytes come from the validated in-memory plan. The installation inventory records the selected adoption record's identity and owner.

## Record shapes

All `Pin` values are exactly `{path, sha256}`, with canonical absolute paths and lowercase SHA-256 of preserved files. Pin bytes must exist and remain current. Authoritative review, acceptance and top-level adoption records must be outside the candidate framework and installation skill/settings directories. A selected evidence outbox elsewhere in the consuming project is supported. The installer does not modify evidence.

`devforge.manual-expert-adoption/v1` has exactly:

- `schema_version`, `project_root` (exact absolute destination), `owner` (actual integration owner), `authorization` (Pin to existing actual user/owner authorization), `packages` (one row per recognized package being installed, no extras or duplicates).
- Each package row has exactly `name`, `manifest`, `specification`, `plan`, `cases`, `creator`, `results`, `decision`, `review`, `acceptance`. All except `name` are Pins.

The runtime manifest has exactly `schema_version: devforge.expert-runtime-manifest/v1`, `name`, and `files_sha256` (complete package-relative runtime file/digest map). It must match precisely the bytes the installer plans to write; evals/history/caches remain source-only. The evaluation's candidate identity binds this runtime manifest. Source structural checks retain their separate full source manifest.

Creator completion has exactly `schema_version: devforge.expert-creator-completion/v1`, `author`, `candidate` (the runtime manifest Pin), `specification` (the same Pin as the adoption row), and `phases`. The latter has exactly Intake, Selection, Design, Authoring, PreparedTransfer. Each has exactly `classification: Enforced` and a nonempty `evidence` Pin array. These records preserve required actions and their actual outputs; a checker does not judge their semantic adequacy.

The evaluator uses the existing generic `devforge.skill-validation-plan/v2`, `devforge.skill-validation-results/v2`, `devforge.skill-validation-decision/v2` and `devforge.skill-ai-review/v2` records. The promoted evaluator documents their full shapes and advisory reducer. This installer consumes their adoption-relevant evidence and requires matching candidate/specification/plan/cases/review/results/decision identities and run ID. Do not use this guard's subset of inspected fields as a replacement schema for producing those records.

The original case catalog uses the existing `cases` or legacy `evals` array. Each case has an `id` and its existing `required_observations`, `expectations`, or single `frozen_discriminator`. Every assertion has a row in the plan's `catalog_assertions`, with matching source Pin, case ID and exact JSON pointer, including every unselected/excluded assertion. Catalog rows and selections must have identical ID inventories. Original C/B/A cases retain N evidence requirements. Additional non-JSON specification anchors must resolve their actual text. The independent selection reviewer assesses complete meaning, variants, arms, applicability and requirement dependencies; mechanical projection does not replace that judgment.

The installer checks fixed P1/T01–T02, P2/T03, P3/T04, P4/T05–T08, P5/T09, P6/T10–T12 coverage and Enforced classification. Required tasks need satisfied evidence; reviewed native exclusions retain NOT_RUN or NOT_APPLICABLE, never native PASS. Required assertions need intact observations and appropriate grade references. Full retains D/S/C/B/A obligations and real target-output/receiver-contract/receiver-observation/completed-action references. The actual operator checks the truth of those observations, including actual user-mediated receiving; the installer does not implement collector authentication.

Routine requires the selected accepted baseline and scope, fixed qualified or accepted unqualified cumulative anchor, linked prior acceptance, immediate/cumulative diff references, CP-01–CP-04 compatibility dispositions, independent selection review and a matching eligible Routine decision. Consequential CI-05/06, unbounded CI-09, explicit Full triggers or a Full claim cannot be relabeled Routine. Routine never moves the qualified anchor. All R01–R10 review records remain present with outcomes and evidence. Author, evaluator and reviewer identities are distinct; actual context independence remains observed evidence, not a name-string guarantee.

Install acceptance is an external owner record with exactly:

```json
{
  "schema_version": "devforge.expert-install-acceptance/v1",
  "owner": "ACTUAL_INTEGRATION_OWNER",
  "project_root": "/absolute/project",
  "package": "devforge-evaluate-expert",
  "action": "install",
  "inputs": {
    "manifest": {"path": "/preserved/runtime-manifest.json", "sha256": "ACTUAL_SHA256"},
    "specification": {"path": "/preserved/spec.md", "sha256": "ACTUAL_SHA256"},
    "plan": {"path": "/preserved/plan.json", "sha256": "ACTUAL_SHA256"},
    "cases": {"path": "/preserved/cases.json", "sha256": "ACTUAL_SHA256"},
    "creator": {"path": "/preserved/creator.json", "sha256": "ACTUAL_SHA256"},
    "results": {"path": "/preserved/results.json", "sha256": "ACTUAL_SHA256"},
    "decision": {"path": "/preserved/decision.json", "sha256": "ACTUAL_SHA256"},
    "review": {"path": "/preserved/review.json", "sha256": "ACTUAL_SHA256"}
  },
  "observation_basis": "operator-reviewed actual evidence"

```

This is an illustrative unpopulated shape, not approval or evidence. The record cannot hash itself. Its exact Pin enters the adoption record after actual acceptance. Neither JSON generation nor a matched owner name establishes an actual owner decision.

## Verification and limitations

Focused tests exercise the real installer with synthetic records: successful exact-byte Full/Routine paths; missing phases/tasks, candidate/evidence drift, missing/omitted assertions, invalid producer/classification/selection, absent transfer, duplicate/malformed input, refusal atomicity and preservation of unrelated configuration. They prove those mechanical predicates only. Native qualification and actual user-mediated skill transfers require separately retained real observations under the accepted Full policy.

Before retiring old operational prototype directories, preserve their complete bytes and inventories, recheck for user edits and compare the selected source mapping. Retirement is limited to identified obsolete skill-builder/skill-validator copies and older creator-only files; no generic cleanup occurs here. Refresh and verify the new installed manifest through the supported installer, then retire verified obsolete copies as an integration-owner action. Do not leave duplicate discoverable workflows and call migration complete.

## Owner-approved unqualified local baseline

The owner may select a separate bounded local acceptance set for the exact pair of manual-mode packages. This is an additional installation claim, not a change to the existing Routine/Full decision rules. It requires the same `--manual-experts-only --manual-evidence RECORD` command and produces `acceptance_status: LOCAL_ACCEPTANCE_SET_PASS`, `qualification_status: UNQUALIFIED` in the result and installation inventory. It cannot authorize an ordinary whole-framework refresh. No `FULL_PASS`, qualification anchor, automatic orchestration or native hook claim follows from it.

The acceptance set freezes before measured observations and requires nine named checks: `package_integrity` (D), `installed_resources` (D), `independent_semantics` (S), and `grounded_creation`, `reuse`, `bounded_enhancement`, `missing_evidence_refusal`, `creator_to_evaluator`, `evaluator_to_creator` (N). Its owner selects concrete expectations, exact package/specification/catalog identities and positive time/native-turn limits before execution. The semantic reviewer checks the meaning and actual evidence; a weak expectation cannot be made sufficient by its hash. Compatible observations may support more than one check, with separate judgments. Native checks require actual Codex observations, complete transcripts/artifacts and observed state isolation. Both receiving checks require actual user initiation, real producer artifacts, observed receiver consumption and completed action. Prepared transfer text is insufficient.

The original five creator phases and six evaluator phases/twelve tasks keep their Enforced classification. This local installation prerequisite does not assert universal phase interception or full qualification of those workflows. The creator remains authoring-only; the evaluator remains read-only toward its target. Full qualification is separate. The local result leaves every original source-catalog case `NOT_RUN` for qualification, even where a related local observation exists. A later Full evaluator can assess compatible raw evidence without rewriting this local result. Historical failures are pinned and retained.

### Local record shapes

All references use the same canonical `Pin` and final freshness/overwrite checks described above. No record hashes itself. The integration owner selects genuine authority and acceptance; fixture data cannot establish either. The installer verifies declared identities and bindings, not the authenticity of people, timestamps or native observations. Actual evidence review remains necessary.

- `devforge.manual-expert-local-baseline/v1`: exactly `schema_version`, `project_root`, `owner`, `authorization`, `packages`, `acceptance_set`, `results`, `review`, `acceptance`, `historical_evidence`. The last field is a nonempty list of Pins to preserved prior evidence; other record references are Pins. Both recognized package names must be present exactly once.
- Each package row: exactly `name`, `manifest`, `source_manifest`, `specification`, `cases`, `author`. The runtime manifest keeps the existing shape and must match installation bytes. The source manifest is exactly `{source_root, files_sha256}`, covering every current canonical package file except Python caches. Source-only additions/deletions also invalidate it. `cases` binds that source's `evals/evals.json`. The guard rechecks the full source inventory immediately before installation.
- `devforge.manual-local-acceptance-set/v1`: exactly `schema_version`, `project_root`, `owner`, `authorization`, `packages`, `checks`, `frozen_at_utc`, `max_seconds`, `max_native_turns`, `historical_evidence`. Identity/authority/history fields equal the adoption record. `checks` maps the nine fixed IDs to `{kind, expectations}`; expectations is a nonempty list of concrete strings. Limits are positive integers. Time is timezone-aware ISO 8601. The set's frozen time precedes the results interval, and every native observation lies within that interval.
- `devforge.manual-local-acceptance-results/v1`: exactly `schema_version`, `acceptance_set`, `qualification_status: UNQUALIFIED`, `checks`, `qualification_cases`, `started_at_utc`, `finished_at_utc`, `native_turns`. `checks` maps each fixed ID to `{outcome: PASS, evidence: [Pin], native_observation: Pin|null}`. D/S use null; N binds its observation among its evidence. `qualification_cases` maps each package name to its complete original case-ID map, with every value `NOT_RUN`. Report actual native turns, including continuations; elapsed time and turns cannot exceed the predefined limits. Never reset the interval or discard a failed attempt to fit.
- `devforge.manual-local-observation/v1`: exactly `schema_version`, `acceptance_set`, `outcome: PASS`, `packages` (name-to-runtime-manifest Pin map), `actor`, `native_client: codex`, `model`, `reasoning_effort`, `state_isolation` (Pin), `transcript` (Pin), `artifacts` (nonempty Pin list), `started_at_utc`, `finished_at_utc`, `manual_transfer`. A receiving observation uses `{direction, user, user_request, producer_output, receiver_observation, completed_action}`; direction is the corresponding check ID, user names the actual initiating user, and the remaining fields are Pins to real evidence. Non-receiving observations may use null.
- `devforge.manual-local-review/v1`: exactly `schema_version`, `reviewer`, `independence_evidence` (Pin), `overall: PASS`, `criteria`, `acceptance_set`, `packages`, `check_judgments`. Reviewer differs from the authors, native actors and integration/test owner; actual context independence must be observed. `criteria` contains R01–R10 and `check_judgments` contains all nine check IDs. Each value is `{outcome: PASS, reason, evidence: [Pin]}`. Each check judgment includes the actual result evidence. Review inputs are the frozen set, packages and raw observations, so no result/review self-digest cycle is needed.
- `devforge.manual-local-owner-acceptance/v1`: exactly `schema_version`, `owner`, `action: install_unqualified_local_baseline`, `qualification_status: UNQUALIFIED`, `inputs`, `observation_basis: operator-reviewed actual evidence`. `inputs` is the complete adoption object before its `acceptance` field is added. Its owner matches the selected record. Conditional user installation authority remains usable after its conditions have actually passed; do not fabricate the owner's decision or ask the same authorization again.

### Cross-allocation evidence reuse

Native observations are normally produced inside the interval of the results record, under one bounded allocation. When an earlier approved allocation was stopped, exhausted or partially completed, its preserved passing observations may be reused in a later results record instead of being re-executed, without rewriting any original record. Reuse is explicit and versioned; the `v1` records above keep their single-allocation behavior unchanged, and Full/Routine adoption is unaffected.

- `devforge.manual-local-acceptance-results/v2`: the `v1` fields plus `allocations` (list of Pins to allocation references) and `reused_observations` (integer). `native_turns` and the `started_at_utc`/`finished_at_utc` interval describe only the current allocation; reused observations are not counted as new executions and are not required to lie in that interval. `reused_observations` must equal the number of distinct reused observation records, and every listed allocation must supply at least one.
- `devforge.manual-local-allocation/v1`: exactly `schema_version`, `allocation_id`, `owner`, `authorization` (Pin, outside candidate and installation roots), `acceptance_set` (Pin), `packages` (name-to-runtime-manifest Pin map), `started_at_utc`, `deadline_utc`, `max_attempts`, `attempts`, `status`, `original_allocation` (Pin), `closeout` (Pin). It is a reference to a preserved allocation, not a replacement for it, and every fact it asserts is compared with the preserved source it pins. The owner, `acceptance_set` and `packages` must equal the adoption record's; the set must have been frozen before the allocation's first native attempt (see the freeze-timing rule below), while the window itself may already have been open for preparation. `status` is the normalized `COMPLETED`, `STOPPED_BLOCKED` or `EXHAUSTED`; the raw closeout status stays as written.
  - `original_allocation` pins the worker's own `allocation.json` as written at the time. Its `started_at_utc`/`deadline_utc` must equal the reference window (compared as instants), its `child_turns` must equal `max_attempts`, and every ledger `attempt_id` must be one of its `slots[].id`. Its `acceptance_set` pin must equal the reference's; when it records none but pins a `prior_allocation`, that prior record's `acceptance_set` is used instead. The approval is linked through whichever form the preserved allocation recorded: when it pins an `authorization`, the reference's `authorization` must be the same pin; when it records the approval only as text, the reference's `authorization` must pin the preserved allocation record itself; when it records the approval as an `approval_ref` pin (the 2026-09-10 remaining allocation), the reference must pin the same file; when it records none and its multi-attempt closeout pins an `authorization` (the 2026-09-10 replacement allocation), the reference must pin that file. Hashing an approval binds its bytes, not its meaning.
  - `attempts` is the complete ledger, in any order, of every attempt made under the allocation, failed ones included: each is exactly `{attempt_id, actor, started_at_utc, finished_at_utc, outcome, launch, completion, evidence: [Pin]}` with a unique ID inside the window. `launch` pins the slot's `launch.json` (its `slot.id` and `started_at_utc` must match) and `completion` pins its `completion.json` (its `finished_at_utc` must match; `outcome: PASS` requires `returncode: 0` and `timed_out: false`). The ledger may not exceed `max_attempts`.
  - `closeout` pins the preserved closeout, read through one of three explicitly supported shapes: `EXPIRED_WITH_PARTIAL_OBSERVATIONS` (`original_started_at_utc`/`original_deadline_utc`, `native_attempts`, optional `slot_states` whose launched entries must agree with each ledger attempt's completion) maps to `EXHAUSTED`; `COMPLETED_BOUNDED_EVALUATOR_RETURN` (`started_at_utc`/`deadline_utc`, `native_turns`, `allocation` pin equal to `original_allocation`, `native_actor`, `launch`/`completion`/`transcript` pins that must match one ledger attempt) maps to `COMPLETED`; `STOPPED_BLOCKED` (`started_at_utc`/`original_deadline_utc`, `attempts_used`, `clock_restarted: false`, a `native` block naming the attempt's role, actor, instants and `workflow_outcome`, and `preserved` pins) maps to itself. The same status is also read in the multi-attempt form the 2026-09-10 replacement closeout recorded: `native` is an array with one entry per attempt (`role`, `actor`, `started_at_utc`/`finished_at_utc`, `launch`/`completion`/`transcript` pins, an optional inline `native_completion` and a `workflow_outcome` only where a judgment was made), there is no `preserved` block, the closeout's `allocation` pin must equal `original_allocation`, and its `authorization` pin, when present, supplies the approval linkage above. In that form the array length must equal `attempts_used`, roles must be unique, every ledger attempt must be named by exactly one entry (by role or launch pin) and every entry must match a ledger attempt, an inline `native_completion` must agree with the pinned completion record, and a `PASS` ledger outcome requires either an entry that records `workflow_outcome: PASS` or a bound subsequent judgment (below): an entry without a judgment and a row without one refuses `PASS` (`preserved closeout records no workflow judgment for the attempt`), because a process exit of 0 is not a judgment. In every shape the window must equal the reference window and the attempt count must equal the ledger length; a native record that says the attempt did not pass forbids a `PASS` ledger outcome; an unsupported status is refused naming the supported ones. Pins inside the original allocation and closeout are verified like any other evidence.
- `devforge.manual-local-allocation/v2`: the `v1` fields, read and checked identically, except that every `attempts` row carries one more field, `judgment`, which is `null` or the Pin of a `devforge.manual-local-attempt-judgment/v1` record. It exists for the 2026-09-10 replacement closeout, whose four native entries preserve executions but no `workflow_outcome`: the closeout keeps saying truthfully that no judgment existed at closeout, and a later reviewer judges the saved outputs in a separate record without editing it. A `v1` reference refuses a `judgment` key and a `v2` row refuses to omit it, so a missing judgment is always explicit. When a row pins a judgment, the row's `outcome` must equal the judgment's `outcome` (`attempt outcome differs from its subsequent judgment`), so an adverse later judgment stays in the ledger and blocks any observation that reuses the attempt. The judgment is validated after the attempt's launch and completion records and before the closeout's native record is compared, so it can satisfy only the no-judgment refusal: a completion with a non-zero exit or timeout (`completion record contradicts the PASS outcome`) and a closeout entry that recorded a failing `workflow_outcome` (`preserved closeout records the attempt as not passed`) still refuse a `PASS` whatever the judgment says. Failed and unjudged attempts, the original instants and the closeout's count and budget are unchanged. A `v2` row may bind a judgment whatever the closeout shape; the judgment only ever satisfies the no-judgment refusal and never relaxes the completion or adverse-record checks.
- `devforge.manual-local-attempt-judgment/v1`: exactly `schema_version`, `reviewer`, `independence_evidence` (Pin), `acceptance_set` (Pin), `packages` (name-to-runtime-manifest Pin map), `original_allocation` (Pin), `closeout` (Pin), `attempt_id`, `actor`, `started_at_utc`, `finished_at_utc`, `launch` (Pin), `completion` (Pin), `evidence` (nonempty Pin list), `outcome`, `reason`, `judged_at_utc`. It must be outside the candidate and installation roots like the review. `acceptance_set` must be the reference's frozen set (the requirements judged), `packages` the adoption record's candidate identity, `original_allocation` and `closeout` the reference's pins, `attempt_id`, `actor`, both instants (compared as instants), `launch` and `completion` the ledger row's, and `evidence` must contain every Pin the ledger row records for the attempt (the transcript and packet), so the judgment names the exact tested packages, requirements, attempt and raw evidence it judged; `judged_at_utc` must be after the attempt finished. The judgment pins only preserved sources and the frozen set, never the reference, results or review, and no record digests itself. Independence is checked explicitly as distinct names plus the pinned `independence_evidence`: the reviewer must differ from the attempt's `actor`, from the adoption owner and from every package `author` (`attempt judgment reviewer is not independent of the attempt actor, package authors or owner`); actual context independence remains observed evidence that the owner examines, not a string guarantee. Refusals name the differing binding (`attempt judgment is for a different attempt`, `... is for a different allocation`, `... bound to a different acceptance set`, `... candidate identity differs`, `... differs from the recorded attempt`, `... omits the attempt's recorded evidence`, `... precedes the attempt it judges`, `unsupported attempt judgment`). A judgment does not replace the nine-check review, a results record or owner acceptance, which remain separate and, where absent, missing.
- `devforge.manual-local-observation/v2`: the `v1` fields plus `allocation` (the Pin of one listed allocation reference) and `attempt_id`. The observation must lie inside that allocation's window, name a recorded attempt whose outcome is `PASS`, match that attempt's actor and exact start/finish instants, and use a transcript that the attempt's ledger evidence already pins. Everything else (acceptance set, candidate identity, outcome, native client, artifacts, state isolation, receiving transfer) is checked exactly as for a current observation.

**Freeze timing (owner-approved 2026-09-10).** For this local, explicitly `UNQUALIFIED` path only, the owner approved: "Preparation may begin before freezing. Requirements, cases and selected skill files must be fixed before the first native attempt in each allocation." (recorded in `tmp/devforge-expert-foundation-20260908/implementation-plan.md`, section "Owner-approved local MVP freeze timing — 2026-09-10", after DevForge PR #10). The guard therefore requires `frozen_at_utc` to be strictly earlier than the allocation's first native attempt, compared as normalized instants, so an equal instant is refused (`acceptance set must be frozen before the allocation's first native attempt`). The first native attempt is the earliest `started_at_utc` across the complete ledger: the closeout's attempt count must equal the ledger length, so the ledger is the whole attempt record, and failed, timed-out, unjudged and unselected rows fix the instant exactly as a selected passing row does. It is neither the ledger's first element nor its first `PASS`. An allocation whose ledger is empty has no first-attempt instant, so no timing verdict is produced and none is invented; such an allocation also admits nothing, because an observation must name a recorded attempt (`reused observation is not a recorded attempt of its allocation`). One function, `frozen_before_first_attempt`, is applied by both `manual-experts` and `check-local-evidence`, so the two commands cannot drift. Original allocation starts, deadlines, caps, counters, closeouts and recorded failures are unchanged, preparation still consumes time from the original allocation start, and Full/Routine qualification policy is untouched. The `report-v2.json` recorded on 2026-09-10 under `tmp/worktree-test-destination-20260910/` stands as the record of what the former freeze-before-window rule refused; an allocation that becomes compatible under the approved rule is not a retroactive original `PASS`, not a reused observation, not a semantic judgment and not acceptance.

The current results interval keeps its separate, stronger rule: the set must still be frozen strictly before `results.started_at_utc` (`acceptance set must be predefined`), and every current observation must lie in that interval. A `devforge.manual-local-observation/v1` current observation carries no allocation reference and no attempt ledger, so there is no complete attempt record to take a first-attempt instant from, and the interval rule is what proves the frozen bytes preceded all in-window work. Relaxing it the same way would need one missing input: a `devforge.manual-local-allocation` reference for the current allocation whose ledger is the complete record of its attempts, bound to a preserved closeout whose count equals that ledger, as the reuse path already requires.

The legacy Python `scripts/manual_expert_adoption.py` is unowned legacy and is not edited by this change. It has no allocation-reuse path at all — it reads only `devforge.manual-local-acceptance-results/v1` — so the freeze-before-first-attempt rule has no counterpart there; its `acceptance set must be predefined` check (line 259) is the results-interval rule, which Rust also keeps unchanged. Its decisions are not framework authority in any case. Authority boundaries are unchanged: the `--authority` record is still verified before and after the evidence read, the protected executable identity still binds the running binary, and the nine checks, the independent review and owner acceptance are untouched.

Refusals include: a `v2` observation under `v1` results (`reused observation requires reuse results`); an allocation not listed in the results (`unlisted allocation`); a missing or stale approval, or an allocation owner, acceptance set or candidate identity that differs; a reference window, cap, status, set or approval that differs from the preserved allocation or closeout; an acceptance set frozen at or after the allocation's first native attempt (`acceptance set must be frozen before the allocation's first native attempt`); an observation or attempt outside its window; an attempt that is not a preserved slot, whose launch or completion record differs, or whose `PASS` label contradicts its completion or the closeout's native record; a ledger longer than `max_attempts` or shorter or longer than the closeout's count; a `v2` row whose judgment binds a different attempt, allocation, set, candidate, actor, instant, launch, completion or evidence, disagrees with the row's outcome, precedes the attempt, names a non-independent reviewer or lies inside the candidate or installation roots; and an unsupported or clock-restarted closeout. One reused observation may support more than one check, but each check still needs its own result row and review judgment. The installation inventory records `reused_allocations`, `reused_observations` and `subsequent_judgments` (the number of reused-allocation ledger rows whose outcome is a bound later judgment) alongside the local acceptance status. As everywhere in this guard, the digests prove which preserved bytes were referenced and that the reference agrees with them; the semantic reviewer and owner still judge whether those observations satisfy the frozen expectations. Known limit: an attempt's `actor` is checked only against a closeout that names one; a closeout without per-attempt native records (the expiry shape without `slot_states`) binds the window and count only.

These local records are not inputs to `assess_evidence.py`'s VPR-2 qualification reducer. The installer consumes them only for the explicitly unqualified local claim. Keep any separately produced Full/Routine plan, results and decision unchanged. A failed local check or unavailable required observation blocks local installation, while reporting and historical preservation remain possible. Native execution still needs its own selected bounded allocation; local adoption permission does not launch an old campaign.

### Local evidence preflight

`devforge install check-local-evidence --project PROJECT --framework FRAMEWORK --packet PREFLIGHT_PACKET --authority AUTHORITY_RECORD` checks whether preserved local-adoption evidence is mechanically consumable by `manual-experts` before anyone spends a native or review turn on it. It calls the installer's own functions (the strict record reader and pin verifier, the package identity binding, the acceptance-set reader, the allocation reference binding with its closeout readers, the observation validator and the final freshness recheck), so it cannot apply different rules; it only differs in what it does with a failure. It does not install, retire, mutate evidence, run candidate code, execute hooks, call a model, modify `PATH` or touch client authentication. The `--authority` record is verified before any evidence is read and again at the end, exactly as for installation; an identity mismatch is a refusal (`BLOCKED`, exit 2, no report), and the running executable and authority record must be outside the project and framework.

`devforge.manual-local-evidence-preflight/v1` has exactly `schema_version`, `project_root`, `owner`, `authorization`, `packages`, `acceptance_set`, `historical_evidence` (the identity fields of the adoption record, compared with the frozen set as installation compares them), `allocations` (a list of `devforge.manual-local-allocation/v1` reference pins, as in `v2` results) and `observations` (a list of `{check, observation}` rows naming a native check and a `devforge.manual-local-observation/v2` pin). No results, review or acceptance record is expected. Reference records are new selection documents written next to the packet; the preserved allocations, closeouts, launches, completions and transcripts they pin keep their bytes and clocks, and a ledger row's `outcome` is the recorded workflow judgment where one exists, the bound subsequent judgment's outcome where a `v2` row pins one, and `NOT_EVALUATED` where neither exists. The packet may list `v1` and `v2` references together.

The report is JSON on stdout: `status` is `COMPATIBLE` (exit 0) only when every check passed, otherwise `BLOCKED` (exit 2). `checks` lists `protected_authority`, `destination_separation`, `packet_record`, `package_identities`, `acceptance_set`, `allocations`, `observations` and `freshness` as `PASS`, `BLOCKED` with the installer's refusal reason, or `NOT_PERFORMED` when a prerequisite failed; a missing required input is a blocker, never a silently skipped check. `allocations` carries one entry per reference with its normalized and raw closeout status, window, cap, complete attempt ledger (ID, actor, instants, outcome, and `judgment`: the bound judgment Pin or `null`) and `earliest_attempt_started_at_utc` (the same minimum the timing rule applies, in the spelling its ledger row used, and `null` when the allocation records no attempt); a judgment that fails its binding blocks the reference through the same `bind_allocation` rules as installation, and its observations are `NOT_PERFORMED`. Every entry, bound or not, also carries `frozen_at_utc`, `rule` (the owner-approved 2026-09-10 timing rule quoted above) and its own disposition: `timing` is `COMPATIBLE` when the set was frozen before the first native attempt, `BLOCKED` when it was not, `NOT_APPLICABLE` when the allocation records no attempt and there is therefore no instant to compare, and `NOT_PERFORMED` when the reference did not bind and its ledger was never read; `timing_reason` states which of those applies. The timing rule is applied after the binding, through the same `frozen_before_first_attempt` the installer uses, so a reference that fails it still reports its preserved instants for the owner's separate decision, and any observation bound to a blocked reference is `NOT_PERFORMED`. `pending` always lists the obligations the preflight does not perform: the results record, the independent nine-check review, owner acceptance, the installation destination checks and quiescence, a native observation for every native check that has none, and the semantic judgment of any observation it did validate. `COMPATIBLE` therefore means only that every mechanical check in this scope passed for the selected bytes; it is not acceptance, qualification, an installation receipt or permission to run a model. Redirecting stdout to a report file is the operator's action.

Rust acceptance tests in `tests/manual_install.rs` cover the multi-attempt closeout through installation and through the preflight, the retained closeout shapes beside it, the approval linkage forms, the no-judgment rule, the replacement closeout's actual shape with no judgment on any entry and a separately recorded subsequent judgment consumed through a `v2` reference (exact binding, contradictory execution evidence, adverse judgments, reviewer independence, preserved closeout bytes and explicit `judgment: null` rows), omitted, duplicate and contradicted attempts, the owner-approved freeze timing (preparation admitted before the freeze when the first attempt follows, through both commands and under a selected test destination; the first attempt taken as the ledger minimum when the failed row is written after the passing one; the strict boundary at an equal instant, including an offset spelling that is only equal after normalization, against a strictly earlier one that is admitted; one compatible and one blocked allocation in the same packet, with only the blocked one's observation `NOT_PERFORMED`; and an allocation with no recorded attempt reported `NOT_APPLICABLE` with a null first-attempt instant, blocking nothing and admitting nothing), independent blockers with dependent checks marked `NOT_PERFORMED`, the authority refusal, and the absence of writes to the project, framework and evidence directories. They are synthetic; the real campaign's records are exercised only through the operator's own packet.

### Selected test destination

The owner-approved local acceptance set binds `project_root` to the historical root it was frozen for. The installation and the preflight require the actual `--project` to be that root; when the owner selects a separate test destination (a Git worktree is the approved default), changing only `--project` refuses (`wrong local installation destination`) and rewriting the frozen set would invalidate every historical reference to its pin. Neither is done. Instead, two record versions carry one additional field that names the selection explicitly; every other rule, record version and Full/Routine behavior is unchanged.

- `devforge.manual-expert-local-baseline/v2`: the `v1` fields plus `test_destination`. `project_root` keeps the historical root, so the unchanged `local set authority/identity differs` equality with the frozen set still holds and the set's bytes, `frozen_at_utc` and pin are untouched.
- `devforge.manual-local-evidence-preflight/v2`: the `v1` packet fields plus the same `test_destination`, consumed by `check-local-evidence` through the same binding function as installation, so the two commands cannot apply different selection rules.
- `test_destination` is exactly `{"historical_project_root": "/abs/historical/root", "path": "/abs/actual/destination", "acceptance_set": {"path": "/preserved/acceptance-set.json", "sha256": "ACTUAL_SHA256"}}`. `historical_project_root` must equal the record's `project_root` (`test destination names a different historical project root`); `acceptance_set` must equal the record's own acceptance-set Pin, path and digest (`test destination is bound to a different acceptance set`), so the selection names the exact unchanged frozen set it redirects; `path` must be absolute and canonical, no `.`/`..` components and no symlink (`noncanonical test destination`), and must equal the resolved `--project` (`test destination differs from the installation destination`). A `v1` record or packet carrying the field, and a `v2` one omitting it, are refused as invalid records; a `v1` record with a different `--project` still refuses as before, so a different destination without this explicit binding is never installed.

The integration owner supplies the selection by writing the `v2` record (and the `v2` packet for the preflight) with the historical root, the selected path and the unchanged set pin; the selected path is copied from the destination preparation the owner accepted, which the guard does not read. Owner acceptance covers the selected destination because `devforge.manual-local-owner-acceptance/v1` `inputs` remain the complete adoption object before `acceptance` is added, now including `schema_version: .../v2` and `test_destination`; an acceptance whose inputs name another destination refuses (`missing exact local owner acceptance`).

Every destination check runs against the actual `--project`, which the selection must equal: separation from the framework (a destination that is, contains or lies inside the framework refuses before evidence is read, in installation and as the preflight's `destination_separation` blocker), the authority record and executable outside it, authority evidence outside its `.agents`/`.codex`/`.claude`, containment of every write, local-edit collisions, inode aliases, the final freshness and authority rechecks, and the `.devforge-install.json` inventory, which is written at the selected destination and records `predicate: manual-local-baseline/v2`, `historical_project_root` and `test_destination` beside the unchanged local acceptance fields; the `INSTALLED` result reports `historical_project_root` beside `project`. The preflight's `packet_record` detail reports both roots and its `pending` destination line names the actual destination. The historical root receives no write, and nothing under it is retired.

Limits: the guard binds paths and digests, not whether the selected destination is a Git worktree or who prepared it; `installed_resources` and the other checks' observations were produced against the historical root, so the semantic reviewer and owner still decide whether they are compatible with the selected destination, and installation-specific verification of installed-resource behavior concerns the actual destination, not the source observations; the historical root's own installation directories are not excluded for authority evidence; the freeze timing rule is destination-independent and every preserved clock, failure and byte is unchanged, so a set frozen at or after an allocation's first native attempt still blocks whichever destination is selected, and one frozen before it is admitted at whichever destination is selected. Rust acceptance tests in `tests/manual_install.rs` cover the redirected installation and preflight with unchanged set bytes and an untouched historical root, the refusal of a different destination without the binding, each mismatched or malformed selection field through both commands, overlapping and symlinked destinations, acceptance that names another destination, and the owner-approved freeze timing under a redirected packet.
